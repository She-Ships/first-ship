# Contributing to First Ship

Thanks for helping grow this list. Every entry directly affects whether someone's first open-source experience feels doable or discouraging — the vetting step isn't bureaucracy, it's the whole point.

## Before you add an issue, check:

- [ ] **It's actually open.** Not closed, not already assigned, not sitting in a stale PR.
- [ ] **It's genuinely beginner-friendly.** Not just labeled "good first issue" — you've read it and believe someone with basic familiarity in the stack could realistically complete it.
- [ ] **The repo is active.** Maintainers respond to issues/PRs within a reasonable window. A good first issue in a dead repo just leads to a PR nobody reviews.
- [ ] **The repo has a Code of Conduct** (or the maintainers are otherwise known to be welcoming to newcomers).
- [ ] **You've added enough context** that someone doesn't have to guess where to start — a pointer to the relevant file/function, or a one-line hint about approach, goes a long way.

## Adding your entry

1. Fork this repo.
2. Add a row to the table in `ISSUES.md`, following the existing format.
3. Use the [issue entry template](./.github/ISSUE_TEMPLATE/first-ship-entry.md) if you want a structured way to draft it first.
4. Open a PR. Tag it `new-entry`.
5. Another community member will do a quick sanity check (mostly: "is this still open and unclaimed?") before merging.

## Removing a stale entry

Issues get claimed or closed. If you notice an entry on the list no longer qualifies, open a PR removing it (or marking it claimed) with a one-line note why. This keeps the list trustworthy — a list full of dead links helps no one.

## Questions

Open a discussion or ask in the she[ships] community. There's no such thing as a dumb question here.
